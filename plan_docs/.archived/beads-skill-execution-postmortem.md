# Beads Skill Execution — Post-Mortem & Findings

Source: `problems.md` (orchestrator CoT trace converting an application plan into a beads DAG via the `plan-to-beads` skill).

## TL;DR

The `plan-to-beads` skill failed end-to-end because of compounding defects:

1. The orchestrator agent has **no `bash` tool** (`bash: false`, `permission: bash: deny`), so when the skill told it to "verify `br --version`" and "execute the script," it abused `playwright_browser_run_code_unsafe` to spawn shell commands before finally delegating.
2. **`br` is not installed** in the orchestratorservice image (where agent sessions run), forcing a full Rust toolchain bootstrap (rustup → nightly → `build-essential` → compile 542 crates) at runtime.
3. The skill teaches the **wrong bead ID format** — it hardcodes `br-<hex>`, but actual IDs are `<prefix>-<hex>` where the prefix is derived from the cwd basename (e.g., `workspace-ryg`). Every captured ID was empty → `br dep add` got empty args → script exit 1.
4. `br` v0.2.15 emits a **transient** JSONL auto-flush warning ("expected canonicalized numbered placeholder") on mutations; the mutation succeeds, and `br sync --flush-only` brings the JSONL back in sync (live status = "In sync").

Plus a separate, larger issue surfaced during the same session: **the `--dir` workspace argument fails when the directory doesn't exist** (named volume mounts `/workspace` empty).

## Beads Storage Architecture (verified live)

Verified against the running stack (`docker compose -f compose.development.yaml exec webhook-receiver …`).

### `br` ≠ Dolt. We run the frozen SQLite+JSONL Rust port.

There are **two** projects that share the "beads" name:

| | `bd` (original, Go, Steve Yegge) | `br` (ours, Rust, Dicklesworthstone) |
|---|---|---|
| Backend | **Dolt** (auto push/pull to remote) | **SQLite + JSONL** (no Dolt, no remote sync) |
| Git | auto-commits, hooks, daemon | no auto-commit — explicit handoff |
| Commit DB state? | **No** (Dolt pitfalls, `.LOCK` bloat, `embeddeddolt/`) | **Yes** — `issues.jsonl` is *designed* to be committed |
| Layout marker | `embeddeddolt/` | `beads.db` + `issues.jsonl` |

`br` is a **deliberate freeze** of the "classic" SQLite+JSONL architecture (per its README: *"frozen at the classic SQLite + JSONL architecture"*; limitations table lists `Dolt backend → SQLite + JSONL only`). The Dolt evolution lives in the Go `bd`/GasTown lineage.

### Live evidence (our system)

```
br 0.2.15          # pinned in Dockerfile.webhook + install-dev-tools.ps1
bvr 0.2.1          # beads_viewer_rust

/workspace/.beads/
├─ beads.db            (SQLite, WAL)
├─ beads.db-wal
├─ issues.jsonl        ← git-tracked
├─ config.yaml         ← git-tracked  (issue_prefix: workspace)
├─ metadata.json       ← git-tracked  (database=beads.db, jsonl_export=issues.jsonl)
├─ .br_history/        ← git-ignored
├─ .write.lock / .sync.lock  ← git-ignored
└─ .gitignore          (831 B — generated by br init)
```
`find … -iname "*dolt*"` in `.beads/` → **nothing.** Confirmed: SQLite, not Dolt.

### Committing the JSONL is `br`'s own design — not a poor decision

`br init` generates `.beads/.gitignore` that **tracks `issues.jsonl` (+ `config.yaml`, `metadata.json`) and ignores `*.db`, `*.db-wal`, `*.lock`, `.br_history/`, `.sync.lock`, merge/daemon artifacts.** The intended workflow (from `br sync --help` and the README) is:

```
br sync --flush-only     # Export database to JSONL (DB → .beads/issues.jsonl); never runs git
git add .beads/          # respects the .gitignore → stages issues.jsonl only
git commit -m "..."
```

So our `plan-to-beads` skill's `git add .beads/ && git commit` step is **correct**. The "don't commit beads state / it auto-syncs via Dolt" guidance (from the AI excerpt) describes `bd`/GasTown, **not `br`** — and `br` has *no* remote sync, so committing the JSONL is also the **only** persistence/transport available (critical given our ephemeral container workspaces).

### `br sync` semantics (from `br sync --help`)

- `--flush-only` — export SQLite → `issues.jsonl` (the default export direction). Idempotent, atomic (temp-then-rename), safety guards (refuses to overwrite non-empty JSONL with empty/stale DB). **Never executes git.**
- `--import-only` — JSONL → SQLite (after `git pull`).
- `--merge` — three-way merge (`beads.base.jsonl` + DB + JSONL); `--force-db/--force-jsonl/--force` resolve semantic conflicts.
- `--rebuild` — treat JSONL as authoritative; removes DB entries absent from JSONL (preserves tombstones).
- `--status` — read-only sync state. Live result: `Dirty issues: 0 … Status: In sync`.

### What reads what

- **Runtime (loop + bvr):** query **`beads.db`** via `br ready --json` / `bvr` (`beads_loop.py` sets `BD_DB=<workspace>/.beads/beads.db`). Neither reads `issues.jsonl`.
- **`issues.jsonl`:** the git-committed/recovery form; SQLite is rebuilt from it on a fresh checkout via `br sync --import-only`.

### Version-tracking is safe on the Rust lineage

`br`/`bvr` are the **frozen classic-architecture** ports. Bumping their versions stays SQLite+JSONL — the Dolt behavior remains in the `bd`/`bv` (Go) lineage. Our pins (`br@0.2.15`, `bvr@0.2.1`) are on the stable lineage; we can track new `br`/`bvr` releases without risk of a silent Dolt migration. (Decision A — shared beads base image — is the place to pin these together.)

### Incidental finding: `core.*` crash dumps in `/workspace`

Three ~1 GB `core.*` files sit in `/workspace` (from the runtime `br`/nightly-Rust bootstrap in the orchestratorservice container — see F2). They should be cleaned and the workspace `.gitignore`'d; not related to beads correctness.

## Detailed Findings

### F1 — Orchestrator has no `bash` tool → Playwright abuse

**Evidence** (`problems.md:26-49`):
```
⚙playwright_browser_run_code_unsafe [code=const { execSync } = require('child_process');
...
⚙playwright_browser_navigate [url=about:blank]
...
Playwright isn't available in this environment. I'll write the complete beads script to a file, then delegate execution to a specialist agent.
```

**Root cause:** `image/.opencode/agents/orchestrator.md` defines:
```yaml
tools:
  bash: false
permission:
  bash: deny
```

The `plan-to-beads` skill (`SKILL.md`) instructs the active agent to *"verify `br --version`"* and *"write and execute a single bash script."* When the orchestrator loads that skill, it has no bash tool — so it reached for the only thing that can spawn a process: the `playwright` MCP's `run_code_unsafe` (which execs Node `child_process`). It burned multiple turns on `about:blank` / `data:text/plain` probes before giving up and delegating.

The orchestrator also shouldn't even have `playwright` available — it's a browser-automation tool irrelevant to orchestration.

**Fix options:**
- **(a)** Rewrite the skill so it explicitly delegates execution: *"You (the orchestrator) do not have a bash tool. Delegate the script execution to the `developer` agent."* This is the targeted fix.
- **(b)** Restrict the orchestrator's MCP access so `playwright` is not even an option (defense in depth).

### F2 — `br` missing from the orchestratorservice image

**Evidence** (`problems.md:87-205`):
```
$ br --version 2>&1
/usr/bin/bash: line 1: br: command not found
...
$ cargo --version 2>&1
/usr/bin/bash: line 1: cargo: command not found
...
$ curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y   # install rustup
$ source "$HOME/.cargo/env" && rustup install nightly && rustup default nightly   # nightly required by beads_rust #![feature]
$ apt-get update && apt-get install -y build-essential                          # C linker
$ cargo install --git https://github.com/Dicklesworthstone/beads_rust.git --tag v0.2.15 beads_rust
$ br --version
br 0.2.15
```

**Why this happened — two consumers of `br` live in two different containers:**

| Image | File | Has `br`/`bvr`? | Consumer |
|-------|------|:--:|----------|
| webhook-receiver | `Dockerfile.webhook` | ✅ (Rust builder stage) | `BeadsLoop` background daemon polls `br ready` |
| host dev machine | `scripts/install-dev-tools.ps1` | ✅ | local validation parity |
| **orchestratorservice** | `Dockerfile` | ❌ | **agent sessions executing the `plan-to-beads` skill** |

`br` was correctly added to the webhook image (the loop daemon's home) and to the host dev machine, but the orchestratorservice image — where agent sessions run and where the skill invokes `br` — was never given it.

**Impact:** Every `plan-to-beads` invocation pays minutes of fragile runtime work installing a nightly toolchain and compiling 542 crates, and it requires `apt-get install build-essential` (network + apt in the container).

**Fix:** Add a Rust builder stage to the orchestratorservice `Dockerfile` mirroring `Dockerfile.webhook` (`Dockerfile.webhook:3-12`), and `COPY --from=rust-builder /usr/local/cargo/bin/br /usr/local/bin/br`. The two consumers then both have a prebuilt `br`.

### F3 — Skill teaches the wrong bead ID format

**Evidence** (`problems.md:259-276`):
```
$ br create "Test Epic" --type epic --priority 1 2>&1
✓ Created workspace-g58: Test Epic
...
The bead IDs use the format workspace-<hex> not br-<hex>. I need to fix the grep pattern in the script:
$ grep -n 'grep -oP' /workspace/.beads/generate_beads.sh | head -5
15:EPIC_P1=$(br create "..." | grep -oP 'br-[a-f0-9]+')
```

**Root cause:** `plan-to-beads/SKILL.md:120`:
```
Bead IDs are printed as `br-<hex>` (e.g., `br-a1b2c3`). Capture them with `| grep -oP 'br-[a-f0-9]+'`.
```
And the example script (`SKILL.md:75,87,98`) uses `grep -oP 'br-[a-f0-9]+'` throughout.

But `br init` (`problems.md:228`) prints `Prefix set to: workspace` — the prefix is **derived from the cwd basename** (the session runs in `/workspace`). In a `/workspace/proj1` session the IDs would be `proj1-<hex>`. So the prefix is dynamic, never literally `br-`. Every `$(br create ... | grep -oP 'br-...')` captured an **empty string**, so every `br dep add <empty> <empty>` failed and the script exited 1.

**Fix:** The skill must capture the token immediately after `Created `:
```bash
EPIC=$(br create "Title" --type epic | grep -oP 'Created \K\S+')
```
Update both the `<cli_reference>` claim and every line in `<example_script>`.

### F4 — `br` v0.2.15 JSONL export error

**Evidence** (`problems.md:231,256,261`):
```
Warning: Mutation succeeded, but automatic JSONL export failed. Fix the export problem,
run `br sync --flush-only`, then commit the updated .beads/issues.jsonl. JSONL path:
/workspace/.beads/issues.jsonl. Error: Database error: internal error: expected canonicalized numbered placeholder
```

**Analysis:** The bead IS created in the SQLite DB (the mutation succeeded), but the **automatic JSONL auto-flush** that `br` runs after each mutation failed with an internal canonicalization error. **Important:** this is the JSONL *export*, which is the git-committed/recovery form — it is **not** what the execution loop reads. The loop (and `bvr`) query `beads.db` via `br ready --json`, so the created beads are still visible and pickable. The skill's prescribed `br sync --flush-only` (`SKILL.md:60-61`) is exactly the documented remediation.

**Verified live:** after the run, `br sync --status` reports `Dirty issues: 0 … Status: In sync`, `br ready` returns the unblocked tasks, and `br list` shows the full graph. So the v0.2.15 auto-flush warning was **transient / non-corrupting** — a subsequent `br sync --flush-only` brings the JSONL fully in sync with the DB. The committed `issues.jsonl` is only at risk if one commits *without* a successful `br sync --flush-only` first.

**Fix / next step:** Ensure the skill always runs `br sync --flush-only` (and checks it succeeds / reports "In sync") before `git add .beads/`. No version bump required for correctness; track the upstream canonicalization warning for a future `br` release.

### F5 — Developer agent actually worked

Contrary to the initial impression that "the developer doesn't have tools," the developer agent (`problems.md:86-205`) **did** have `bash` and used it correctly throughout (installed rustup, nightly, build-essential, compiled `br`). The perceived "no tools" was actually F2 (the agent had bash, but `br` wasn't there, so it bootstrapped a toolchain). The only agent misbehaving was the **orchestrator** (F1).

## Related: `--dir` workspace argument fails (separate issue)

When invoking with `-Workspace "/workspace/proj1"`, `opencode run --dir` errors that the directory doesn't exist — which is true.

**Root cause:** `compose.yaml` mounts `opencode-workspace:/workspace` as a **named volume** (empty). `scripts/prompt.ps1` passes `--dir $Workspace` straight to `opencode run --attach`. The `--dir` path is resolved **server-side** (inside the container where the session runs), so `/workspace/proj1` must exist inside the orchestratorservice container. Nothing creates subdirectories, and a named volume isn't a host path the host script can `mkdir`.

**Fix options:**
- **(a)** Launcher creates the dir in the container before attach: `docker compose exec orchestratorservice mkdir -p /workspace/proj1`.
- **(b)** `prompt.ps1` detects a container/server target and `mkdir`s via `docker exec` against the server container.
- **(c)** Switch `/workspace` from a named volume to a host **bind mount** so the host path exists and persists.

> **Decision: Option (c) — host bind mount.**
>
> Replace the named volume in `compose.yaml` with a bind mount sourced from a host env var, e.g.:
> ```yaml
> volumes:
>   - ${WORKSPACE_DIR:?WORKSPACE_DIR is required}:/workspace
> ```
> and remove `opencode-workspace` from the `volumes:` top-level block. This gives host-side visibility and persistence of agent working trees.
>
> **Subdir creation is still required.** `opencode run --dir /workspace/proj1` requires the dir to pre-exist; opencode does not auto-create it. With a bind mount the path has a **host equivalent** (`$WORKSPACE_DIR/proj1`), so the launcher / `prompt.ps1` can `mkdir -p` it directly on the host (e.g. `New-Item -ItemType Directory -Force "$WORKSPACE_DIR/proj1"`) before invoking `opencode run --dir /workspace/proj1` — no `docker exec` needed. `prompt.ps1` should derive the host path from `$WORKSPACE_DIR` (strip the `/workspace` prefix and prepend `$WORKSPACE_DIR`) and ensure it exists before attach.

## Decisions

| # | Finding | Chosen fix |
|---|---------|-----------|
| F2 | `br` missing from orchestratorservice image | **Option A** — shared beads base image (single Rust build, two consumers) |
| `--dir` workspace | Subdir doesn't exist | **Option C** — host bind mount + host-side `mkdir -p` |

### Decision A — Shared beads base image (F2)

The three bead toolchains (`Dockerfile.webhook`, `install-dev-tools.ps1`, and the missing orchestratorservice copy) are **disparate recipes with aligned versions** (both existing ones pin `beads_rust@v0.2.15`, `beads_viewer_rust@v0.2.1`, nightly). They are duplicated definitions with no single source of truth, so they can drift.

**Decision: build a dedicated base image once and consume it in both container Dockerfiles.**

- Add `Dockerfile.beads` — a Rust builder producing `/usr/local/bin/br` (and `bvr`).
- Publish it (e.g. `ghcr.io/<org>/beads:0.2.15`) via a `publish-beads` pipeline.
- In **both** `Dockerfile` and `Dockerfile.webhook`, replace the in-tree Rust builder stage with:
  ```dockerfile
  COPY --from=ghcr.io/<org>/beads:0.2.15 /usr/local/bin/br /usr/local/bin/br
  ```
  (orchestratorservice needs only `br`; the webhook image also wants `bvr`.)
- `install-dev-tools.ps1` keeps building locally for host dev parity (or also pulls the published binary).

This fixes the original bug (orchestratorservice gets `br`), removes the runtime bootstrap, and makes the pinned versions a single source of truth.

### Decision C — Host bind mount + host-side subdir creation (`--dir`)

See the "Related: `--dir` workspace argument fails" section above. Switch `/workspace` to a host bind mount (`${WORKSPACE_DIR}:/workspace`); the launcher / `prompt.ps1` `mkdir -p`s the project subdir on the host before attach.

## Recommended Fix Order

1. **Pre-install `br` via shared base image** (F2, Decision A) — scaffold `Dockerfile.beads` + publish pipeline, `COPY --from` in `Dockerfile` and `Dockerfile.webhook`. Unblocks every `plan-to-beads` run; removes minutes of runtime bootstrap; unifies the three recipes.
2. **Fix the ID-format bug in `plan-to-beads/SKILL.md`** (F3) — `grep -oP 'Created \K\S+'` everywhere. Without this the DAG script can never capture IDs even once `br` exists.
3. **Add explicit delegation instruction to `plan-to-beads/SKILL.md`** (F1) — "You have no bash tool; delegate script execution to the `developer` agent." (Optionally restrict orchestrator MCP access to `playwright`.)
4. **Ensure `br sync --flush-only` runs + succeeds before commit** (F4, resolved) — the v0.2.15 auto-flush warning is transient/non-corrupting; the skill must verify "In sync" before `git add .beads/`. No version bump needed; commit-JSONL is correct (see "Beads Storage Architecture").
5. **Switch `/workspace` to a bind mount + host-side `mkdir`** (Decision C) — `compose.yaml` bind mount; `prompt.ps1` ensures `$WORKSPACE_DIR/proj1` exists before attach.

Items 1–3 and 5 are clear-cut and ready to implement. Item 4 is upstream.
